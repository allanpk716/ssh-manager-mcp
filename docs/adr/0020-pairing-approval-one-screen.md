# 权威端配对批准在一个界面完成

owner 在权威端 Web UI 批准新客户端时，旧流程要先打开列表，再进入单条表单；超过重新验证窗口时还要输入管理员口令并回跳。端口映射、反向代理或容器网络部署还会让客户端声明的对外地址永远不属于本机网卡地址，于是 owner 每次都被要求输入精确覆盖文字。例行警告会削弱人工判断，也让批准体验不可用。

## Decision

**一、批准与拒绝配对不再要求近期重新验证管理员口令。** 这两个操作仍要求有效的权威端 Web UI 登录会话、防跨站请求伪造校验与审计；其他敏感写操作继续保留近期重新验证。这样 owner 在看到客户端屏幕时，可以立即在配对列表完成裁决。

**二、配对列表页直接完成比对与裁决。** 每条待批准请求在列表内大字显示实例名、客户端连接的权威端地址、6 位短认证码与剩余时间，并提供 Profile 选择、「我已逐位比对三项一致」勾选、批准和拒绝按钮。只有一个 Profile 时默认选中；提交失败时停留在列表、显示错误并保留已选 Profile。单条详情页保留为直达链接，但不再是必经步骤。

**三、本机地址集合可登记对外地址，Web UI 不再提供覆盖文字输入。** 新设置项 `serve.public_addresses` 接受逗号分隔的「主机」或「主机:端口」；只写主机时任意端口都算本机，写了端口时端口必须相同，IPv6 地址用方括号书写；环回地址与未指定地址不能登记，环回目标仍一律判为异常。地址不属于本机集合时，Web UI 只显示拒绝按钮，后端也拒绝批准；显式放行只保留在命令行 `serve pair approve --allow-foreign-url`。

## Considered Options

- 继续要求输入精确覆盖文字。端口映射部署会每次触发警告，owner 会被迫把覆盖当成固定操作步骤，安全提示失去区分度，因此没有采用。
- 彻底去掉机械地址检查，只留人工提示。6 位短认证码可被同时控制两条密钥交换腿并更换密钥的中间人离线研磨；只靠提示无法挡住假发现与透明转发场景，因此没有采用。
- 让 Web UI 继续提供显式放行按钮。异常地址本身表示客户端可能连到另一台机器；若浏览器界面允许放行，例行的点击仍会替代调查，因此只保留命令行显式放行。

## Consequences

- 批准与拒绝配对的残余风险变为：他人拿到已登录浏览器即可操作。但攻击者还需要控制一台正在发起配对的客户端，且成功或失败都会留下权威端审计行。
- 端口映射、反向代理或容器网络部署应把客户端实际连接的地址登记在 `serve.public_addresses` 中；登记与删除走既有设置审计。
- 陌生地址在 Web UI 中只能拒绝。确属受控转发网络时，owner 先登记地址并重新核对，或在权威端主机上使用命令行显式放行。
