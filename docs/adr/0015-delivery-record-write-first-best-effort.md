# 下发记录作为受审计转发写的第三员,先写文件后登记,登记失败不阻断写入

受审计转发写原有两员(锚定转发、元数据编辑)的语义是:权威 broker 不可达就直接失败,不排队、不留本地状态。下发记录(哪个机密项经 `upload_content` 填值后写到了哪台服务器条目的哪个路径)要在权威端可见,才能支撑删除机密项前的影响预览和第二版的换值后重写、发现手工改动;但填值与写入都在客户端完成,并且已经定下 broker 不可达时用缓存值照常写入(票「机密项:在哪一侧填值」)。两条规则在这里冲突。我们决定(2026-10-31 grilling 定案,地图「机密项:agent 部署含敏感信息的配置而值不经过 agent 上下文」的票「机密项:下发记录的落点」):

1. **下发记录是受审计转发写的第三员**:客户端写完文件后经设备码认证把记录发给权威 broker,broker 在单个事务里落库并写审计行;单机部署直接写本机 vault。记录只存在 vault,不在客户端另留一份。
2. **先写文件,后登记;登记失败不回滚写入**:broker 不可达或校验不通过时,文件照常写入,`upload_content` 的结果里给出登记状态「未登记」和原因。不排队、不在本地暂存后补发,沿用受审计转发写「不留本地状态」的约束;本地审计只做镜像补记。
3. **broker 落库前校验**:服务器必须同时在该机密项的可写入服务器列表内和这台设备 profile 授权的服务器内,否则拒绝落库并写审计行。客户端写入前已拦截过,这一步防的是客户端缓存过时(例如授权刚被撤销)。

否决的做法:
- **登记失败则整个写入失败**:与受审计转发写原语义一致,但让机密项的写入在 broker 不可达时完全不可用,违背填值票的离线可写结论。
- **本地暂存,broker 恢复后补发**:引入受审计转发写明确禁止的本地排队状态,还要处理补发时授权已变化的情况。

## Consequences

- 下发记录可能缺漏:broker 不可达期间的写入没有记录。删除机密项前的影响预览因此不保证完整;第二版发现手工改动的检查可以兜底一部分。
- 受审计转发写不再是统一的「不可达即失败」:三员里只有下发记录在 broker 不可达时让主操作照常完成。以后新增成员时要逐个说明属于哪种语义。
- 旧客户端不填值,也就不登记,不产生下发记录(ADR 0014)。
