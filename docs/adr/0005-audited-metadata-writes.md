# 客户端元数据编辑:受审计转发写从「仅可新增」扩展到「乐观锁更新」

服务器条目的六个元数据字段(Role/Services/Location/Hardware/Caveats/Description)读面向 agent(list_servers 全量可见)、写却只属于 owner(权威端 TUI/CLI),探明服务器的 agent 无法把发现记回,元数据靠人肉登权威端维护而腐化。我们决定:**客户端经设备码认证发起元数据部分更新,权威 broker 以 revision 乐观锁(单调整数列,一切 UPDATE servers 路径统一自增)做 CAS,冲突 409 并附六字段现值供一跳重试;变更与审计行(骨架+每字段旧值截断 200 字节)同事务落库;写成功后本地只读快照经第二个窄写口镜像补记,不产生第二事实源;全局开关(serve --metadata-edit / SSHMGR_SERVE_METADATA_EDIT / serve.metadata_edit)默认开**。批 1 只挂客户端缓存脸的 MCP 工具,批 2 再补客户端 CLI/TUI 表单(同路由)。这是锚定转发(ADR 0002)确立的「设备码认证的受审计写」模式从 insert-only 到条件更新的扩展——写类别升级,护栏相应升级(乐观锁替代仅可新增)。

## Considered Options

- **维持 owner 端独占写**:被否——零仪式诉求的反面,元数据腐化是既成痛点,且 owner 端编辑的维护成本随条目数线性涨。
- **本地可写覆盖层 / 离线暂存后补写**:被否——破坏多机同步零合并约束(ADR 0002 同款否决),元数据比锚更高频变更,本地可变状态的合并复杂度更不可接受。
- **最后写赢(无乐观锁)**:被否——owner TUI 手改与 agent 自动写在同秒/跨秒都会静默互踩,「锁装了但同秒不锁」(updated_at unix 秒做令牌)同罪,故新列。
- **Web 管理界面(Plan 42 批 2)**:被否/延后——入口在 agent(它正是发现信息的一方)最彻底,人肉路径批 2 补 CLI/TUI。
- **全字段必填写(非部分更新)**:被否——强迫 agent 默写未探明字段,抄错即抹数据;缺席=保持/空串=清空的部分语义无损覆盖。

## Consequences

- **信任面扩张(如实承认)**:持有效设备码者从「只读快照+仅可新增锚」扩到「可改绑定 profile 授予条目的六个元数据字段」。补偿控制而非消除:仅元数据(tags/连接字段/凭据不开放,改地址/换凭据的结构性风险不进门);条目须在设备码绑定 profile 授予集合内;revision 乐观锁使 owner 与 agent 互踩必被 409 暴露;审计行带设备名与旧值截断(写坏多半可手工改回,隔夜灾难由每夜备份兜底);开关可全局关;吊销设备码即整体收权。
- **误写检测面**:409 body 附六字段现值——零泄露(信息 ⊆ 该设备码下一次快照拉取可自算的内容),换来 agent 无需 cache pull 的一跳自愈;旧缓存(revision 一律读 0)同样一跳收敛。
- **「变更属于服务端」原则修正为「变更属于服务端,两条受审计转发写通道(锚定/元数据)除外」**;只读哨兵 ErrReadOnly 文本不动(窄写口不经过它)。
- **revision 成为跨版本协议字段**:快照/导入/备份全链携带,旧形态一律回填 0;一切 UPDATE servers 的写路径(含未来新增的)必须自增——这是守护乐观锁正确性的不变式,新写路径漏 bump 等于撤防。
- 审计 OwnerOnly 巡检面混入设备发起的 meta-edit 行(project_id 为空;项目归属是客户端自称不可验证,拒绝采信)——与 pin-forward 同款,以 action 名可筛,有意。
