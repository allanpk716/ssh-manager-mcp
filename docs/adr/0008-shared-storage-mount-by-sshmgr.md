# 共享存储:由 sshmgr 代为挂载,密码沿用机密项,不让 agent 自己拼挂载命令

多台受管服务器需要共用局域网或虚拟局域网里的网络共享(首版只做 SMB)存放大数据和临时数据,过去每台机器都要 owner 手工配置连接。我们决定:**owner 在权威 vault 登记共享存储(提供方设备、共享名、目录约定、挂载点约定;候选访问地址来自提供方设备在网络拓扑里的各个网络成员地址,不单独登记),挂载账号的密码存为机密项;sshmgr 提供挂载工具,按目标服务器的操作系统自己生成并执行持久挂载(Linux 写仅 root 可读的凭据文件和 `/etc/fstab`;macOS 写 autofs 间接映射;Windows 在每条命令执行前于同一会话内调用 `New-SmbMapping` 注入网络盘符——见下文「各系统的挂载方式」),密码由 sshmgr 在内部填入,不经过 agent 上下文**。能挂载哪些服务器,沿用该机密项的「可写入服务器列表」,列表内无需逐次确认。

## Considered Options

- **只登记,由 agent 自己执行挂载命令、sshmgr 代填密码**:被否——Windows 的 `net use` 和 `cmdkey` 必须在命令行里带密码,这会逼着机密项去支持命令行代填,扩大机密项的安全面(命令文本会进入命令策略检查、审计日志)。
- **不挂载,sshmgr 自己连接共享,用中继在共享和服务器之间搬文件**:被否——大数据全部经过 broker 内存中转,成为瓶颈;而且服务器上的程序无法把共享当作普通目录使用。
- **另设一份「可挂载服务器名单」**:被否——挂载本质就是把密码写进那台服务器,与「可写入服务器列表」含义相同,两份名单迟早不一致。

## Consequences

- 挂载工具必须幂等(已挂载且配置一致即成功;写远端配置时加文件锁),因为多个会话、多台客户端机器可能同时挂载同一台服务器。
- agent 只能挂载,不能卸载:挂载被一台服务器上的所有会话共用,卸载会打断其他会话,所以卸载、撤销、重选地址与残留检查只在 owner 的命令行里提供。
- 权威端不记录各服务器的挂载状态,唯一事实源是服务器本身;改密码后的「重新下发」与「已移出列表但仍挂载」检查都靠逐台现场探测。
- 只收能持久挂载的协议;FTP 这类有会话数限制、空闲会被断开的协议不进入此机制。
- **多个 sshmgr 进程并发**(每个 agent 会话一个桥进程,多台客户端机器同时操作同一目标):挂载工具不改写仍可连通的地址(改地址等于卸载再挂载,会让 agent 间接获得卸载能力),切回更优地址由 owner 执行 `shares reselect`;目标机上的挂载配置带共享存储版本号标记,快照落后的进程不得覆盖(只适用于 Linux / macOS,Windows 目标机上不留标记);Windows 注入遇认证失败即暂停,直到该共享版本号变化,避免旧密码反复尝试触发 NAS 按 IP 封锁;登记共享存储的前提是关闭 NAS「禁止同一 IP 多个连接」开关。
- **撤销**(owner 取消某台服务器的授权):可写入服务器列表的变化也让共享存储版本号加一。Linux / macOS 先删凭据与挂载配置、留下不含密码的撤销标记(挡住旧快照进程重新写入),再按 owner 选择决定是否卸载;服务器连不上不排队,靠 `shares residue` 现场检测兜底。Windows 撤销就是停止注入,随快照同步生效,离线客户端在同步前仍会注入——护栏而非安全边界;真正的撤销手段是改共享密码。

- **挂载在整台机器上可见**(2026-10-31 补充):可挂载范围按服务器条目登记,但一台设备可关联多个条目(同一台机器的不同登录用户),挂载发生在机器上;同设备上未勾选条目的登录用户能否读到共享内容取决于挂载的文件权限,sshmgr 不按登录用户隔离。Web UI 共享详情页勾选条目时,若同设备还有未勾选的条目,提示「同设备的其他条目可能也能读到」。
- **删除提供共享存储的设备**(2026-10-31 补充):不再拒绝,改为级联删除——设备上的共享存储一并删除,对可挂载范围内每台 Linux 与 macOS 服务器走上面的撤销流程;Windows 服务器随快照同步停止注入。挂载密码机密项保留,真正撤销仍靠改密码。删除前的预览按共享存储逐项列出可挂载范围内的每台服务器(条目名、所属设备、系统类型),即撤销流程将去卸载或停止注入的机器;因挂载状态不留记录,列的是范围而非已挂载的现状。远端失败或挂载被占用不回滚登记删除,结果提示用 `shares residue` 检查、用 `shares unmount --force` 补清理。

## Owner 命令语义

四个命令都只在持有已解锁可写 vault 的机器上执行;缓存客户端拒绝。这些命令的输出与 owner 审计不包含共享地址、挂载账号或密码;除残留检查外,审计在有已知共享存储版本号时记录它,并记录是否强制,撤销审计另记录是否更换了密码。

### `shares unmount SHARE SERVER [--force] [--yes]`

只作用于 Linux 与 macOS 服务器。它先删除 sshmgr 生成的持久配置(Linux 是凭据文件与 `/etc/fstab` 行,macOS 是 autofs 映射条目),再卸载 `/mnt/sshmgr/<共享名>`;顺序保证卸载失败后配置也不会把共享自动挂回。默认遇到占用进程时保留挂载并列出进程号、用户与命令名;`--force` 表示强制卸载(Linux 先强制卸载,失败后延迟卸载;macOS 使用系统的强制卸载)。

服务器仍在该共享的可挂载范围内时不写撤销标记,并提示 agent 之后仍可能重新挂载;彻底撤下授权要用 `shares revoke`。服务器已不在范围内或共享登记已删除时会写撤销标记,用来挡住仍持旧快照的 `mount_share`。Windows 服务器被拒绝,因为 sshmgr 不在其上留下持久配置。

### `shares revoke SHARE SERVER [--unmount] [--force] [--new-password-stdin | --new-password-from-file <路径>] [--yes]`

第一步先提交登记变更:把服务器从挂载密码机密项的可写入服务器列表移出,共享存储版本号加一;若同时提供新密码,则换密码也在同一事务里,这次合并变更仍只让共享存储版本号加一。新密码只能从标准输入或文件按字节读入,不会进入命令参数。

对 Linux 与 macOS 服务器,登记提交后总会尝试删除远端持久配置并写撤销标记;`--unmount` 决定是否接着卸载。不带它时现有挂载保留;带它时默认被占用则保留并列出占用进程,`--force` 才强制卸载。服务器连不上时立即失败、不排队,登记变更保留,错误指向 `shares residue`。对 Windows 服务器不发起连接;各客户端同步快照后停止注入,在线客户端默认 5 分钟内生效,正在执行的命令保留盘符直到结束,长期离线的客户端同步前仍会注入。

同时换密码时,命令列出仍在可挂载范围内的其余 Linux 与 macOS 服务器——它们要等 agent 按新共享存储版本号调用 `mount_share` 才会用新密码;桌面上手动添加的共享连接也要由 owner 更新密码。

### `shares reselect SHARE SERVER [--force] [--yes]`

只作用于仍在该共享可挂载范围内的 Linux 与 macOS 服务器。候选顺序与 `mount_share` 相同:物理局域网地址优先,同级按登记顺序,并在目标服务器上探测服务器消息块协议使用的 TCP 445 端口。当前地址已是最优可达地址时不改动;否则在服务器级挂载锁内用新地址改写配置,再卸载并重新挂载。默认遇到占用进程时保留旧地址、旧配置与挂载并列出进程;`--force` 才强制卸载后重挂。Windows 服务器不需要重选,因为每条命令执行前本来就会重新选址与注入。

### `shares residue [SHARE]`

只读检查 vault 里的全部 Linux 与 macOS 服务器条目,一次最多并发检查 4 台。它枚举服务器上的 sshmgr 版本标记、Linux 凭据文件、autofs 或 `/etc/fstab` 配置、现有挂载与撤销标记,再与当前登记比对:共享登记已删除,或服务器不在该共享的可挂载范围内,才报告残留;每条残留附完整的 `shares unmount` 清理命令。只有撤销标记时报告为「仅有撤销标记」,这是撤销后的预期状态,不需要清理。连不上的服务器列为未检查;Windows 服务器跳过并说明 sshmgr 不在其上留下任何东西。

### 撤销标记

Linux 与 macOS 的撤销标记都是仅 root 可读(`0400`)的文件,内容固定为:

```text
sshmgr-share=<百分号编码的共享名>;sshmgr-version=<十进制共享存储版本号>;sshmgr-state=revoked
```

它不含共享地址、挂载账号或密码。`mount_share` 在挂载锁内读取标记:标记版本号不低于调用方快照里的共享存储版本号时拒绝重新挂载;快照版本号更大则照常挂载,成功后删除标记,重新授权随之生效。root 用户仍可直接删除标记或使用既有挂载,因此它是防旧快照回写的护栏,不是被入侵服务器上的安全边界;安全撤销要更换共享密码。

## 各系统的挂载方式(2026-10-31 补充,依据真机验证)

- **Linux**:`/etc/fstab` + 仅 root 可读的凭据文件,选项含 `_netdev,nofail,x-systemd.automount` 与 `x-systemd.mount-timeout`;SMB 协议版本由挂载工具在目标机上按 3.1.1 → 3.0 → 2.1 → 2.0 依次试出后写入,不作登记字段、不回写权威端。
- **macOS**:autofs **间接映射**挂在 `/mnt/sshmgr`,密码按 URL 编码写进权限 600 的映射文件。不用 LaunchDaemon:间接映射免建目录、抗重启、无人登录可用。系统升级可能重置 `/etc/auto_master`,不做主动监控——现场检测发现条目缺失即报告未挂载,挂载工具每次调用都重建配置。
- **Windows**:密钥认证的 SSH 会话是网络登录,无法存凭据,每次执行命令又是新的登录会话,不存在「配置一次、此后会话自动可用」的做法(计划任务、SYSTEM 账户路线均经真机证伪)。因此 sshmgr 在**每条命令执行前于同一会话内调用** `New-SmbMapping`,对目标机所在可写入服务器列表内的全部共享存储自动注入固定盘符,不在服务器上留任何东西;不需要、也不索取 Windows 登录密码。挂载密码经会话标准输入送入远端封装,不出现在目标机进程命令行中。注入失败不阻止命令,只附警告;审计只记录已注入的共享名,不记录地址、账号、密码与注入步骤文本;注入步骤不进命令策略检查。挂载点约定是 owner 登记时为每个共享存储指定的固定盘符(同一 vault 内不重复),不含地址。代价:桌面会话、服务、计划任务、SFTP 文件传输和命令结束后仍在运行的后台进程都看不到这个盘符;owner 自己的电脑改由 Web UI 的桌面手动添加引导解决;引导不显示共享存储密码(机密项的值只写不读),提示 owner 输入自己保存在密码管理器里的密码。
- Linux 与 macOS 的挂载点约定统一为 `/mnt/sshmgr/<共享名>`。

### 被否的 Windows 候选

- **计划任务代存凭据**:免密码变体能把凭据写进凭据管理器,但 SSH 会话枚举不到、也用不上;带登录密码的变体存的凭据同样在交互侧。还要索取 Windows 登录密码,得不偿失。
- **`C:\sshmgr\<共享名>` 目录符号链接**:需要管理员权限,链接目标含地址、地址一变就要重建,且在服务器上留下持久文件;盘符不含地址、无需探测即可推算。
