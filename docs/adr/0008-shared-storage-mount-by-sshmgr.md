# 共享存储:由 sshmgr 代为挂载,密码沿用机密项,不让 agent 自己拼挂载命令

多台受管服务器需要共用局域网或虚拟局域网里的网络共享(首版只做 SMB)存放大数据和临时数据,过去每台机器都要 owner 手工配置连接。我们决定:**owner 在权威 vault 登记共享存储(访问地址、共享名、目录约定、挂载点约定),挂载账号的密码存为机密项;sshmgr 提供挂载工具,按目标服务器的操作系统自己生成并执行持久挂载(Linux 写仅 root 可读的凭据文件和 `/etc/fstab`;Windows 与 macOS 的具体机制另行决定——密钥认证的 SSH 会话里 `cmdkey` 无法保存凭据),密码由 sshmgr 在内部填入,不经过 agent 上下文**。能挂载哪些服务器,沿用该机密项的「可写入服务器列表」,列表内无需逐次确认。

## Considered Options

- **只登记,由 agent 自己执行挂载命令、sshmgr 代填密码**:被否——Windows 的 `net use` 和 `cmdkey` 必须在命令行里带密码,这会逼着机密项去支持命令行代填,扩大机密项的安全面(命令文本会进入命令策略检查、审计日志)。
- **不挂载,sshmgr 自己连接共享,用中继在共享和服务器之间搬文件**:被否——大数据全部经过 broker 内存中转,成为瓶颈;而且服务器上的程序无法把共享当作普通目录使用。
- **另设一份「可挂载服务器名单」**:被否——挂载本质就是把密码写进那台服务器,与「可写入服务器列表」含义相同,两份名单迟早不一致。

## Consequences

- 挂载工具必须幂等(已挂载且配置一致即成功;写远端配置时加文件锁),因为多个会话、多台客户端机器可能同时挂载同一台服务器。
- agent 只能挂载,不能卸载:挂载被一台服务器上的所有会话共用,卸载会打断其他会话,所以卸载只在 owner 的 CLI 和 TUI 里提供。
- 权威端不记录各服务器的挂载状态,唯一事实源是服务器本身;改密码后的「重新下发」与「已移出列表但仍挂载」检查都靠逐台现场探测。
- 只收能持久挂载的协议;FTP 这类有会话数限制、空闲会被断开的协议不进入此机制。
