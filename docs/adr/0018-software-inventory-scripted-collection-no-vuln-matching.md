# 软件清单用固定只读命令采集，sshmgr 不做漏洞比对

owner 要用外部的漏洞订阅程序判断哪些设备受某条漏洞公告影响，sshmgr 为此提供结构化的软件清单。这里定了两件事。

## Decision

**一、日常的实测采集由采集执行者跑固定的只读命令完成，不交给 AI agent。** 采集执行者默认是权威端，权威端没有网络路径的设备可以指定一个客户端实例。这样做的理由有四条：
- 每次采集的命令和解析规则都一样，前后两次结果可以逐条比出变化；
- 不消耗 token；
- 版本号原样读自包管理器和注册表，不会被编造；
- 命令集事先审查过，没有临场发挥的副作用。例如 Windows 上的 `Win32_Product` 查询会触发 MSI 安装包修复，固定命令集里可以事先排除它。

agent 只在 owner 专门要求时出场，用来认领未识别进程、起草声明，结果由 owner 确认后才生效。

**二、sshmgr 只提供软件清单和导出，不接收漏洞公告，也不做版本比对。** 漏洞库、名称对齐、受影响版本区间的判断，都交给外部程序。sshmgr 能保证的只有清单本身：版本精确、来源可追溯、给出标准标识(软件包统一地址)，导出格式是 CycloneDX。

## Considered Options

- 由 agent 定期 SSH 上去盘点。它擅长认出非标准安装的软件，但输出不稳定，变化无法比较，还会持续消耗 token，因此没有采用。不过它的长处被保留在「认领未识别进程」这一环。
- sshmgr 内置漏洞比对，在 Web UI 里直接显示受影响的设备。这样 sshmgr 就要跟进漏洞库和版本区间的语义，越出了它「配置中心」的职责，因此没有采用。

## Consequences

- 包管理器和注册表认不出的软件，只要监听了端口，就会以未识别进程的形式出现；不监听端口的手工安装软件采不到，只能靠声明补上。
- POSIX 固定命令集始终由 `/bin/sh` 解析；目标账户登录 shell 是 zsh、fish 还是 bash，都不改变脚本行为。
- 暴露级别中的局域网、虚拟局域网、公网三档，实测无法判定，只能来自声明。

## 补记(owner 2026-11-20)

实际使用后 owner 认为界面过于复杂，收窄为「只提供清单」:声明清单、认领、「对不上」与待确认暴露暂停使用(数据结构保留);导出改为平铺总表 CSV(每行一台设备上的一个软件条目)，CycloneDX 降为可选;查询增加「软件名 + 精确版本」条件，「是否低于某版本」仍不由 sshmgr 判断;全部设备每天定时采集，默认凌晨 1 点，可改。

## 补记(owner 2026-11-21)

实际用下来，清单 598 行里一半以上是没有版本号的未识别进程和 Windows 系统自带服务，人和 agent 都无法据此判断风险。调整为两层：

- **重点清单**给 owner 和 agent 排优先级：操作系统与内核、监听端口的程序(每个程序一行)、容器、驱动与固件、待装安全更新数量。Windows 系统自带服务不单独成条，其监听端口并入操作系统条目(带暴露级别、参与监听排序)；系统端口暴露的风险取决于操作系统补丁，挂在操作系统条目上正好对应这层语义。
- **完整数据**以 CycloneDX 交给外部扫描工具(Trivy、Grype、OSV):软件包统一地址带发行版信息，因为发行版会把安全修复向后移植进旧版本号，只看上游版本会误判。CycloneDX 由「可选」恢复为机器比对的主格式;CSV 只导出重点清单。

本 ADR 第二条「sshmgr 不做漏洞比对」不变：考虑过内置 CISA 已被利用漏洞目录(KEV)的产品名单并在清单上标注，没有采用，名单由外部 agent 自带。新增的「待装安全更新」读的是包管理器本地缓存，是事实而非 sshmgr 的判断，因此不违反本条。

明确不做：进容器采集(需 docker exec，越出固定只读命令集)、在服务器上安装扫描工具、应用内部的语言级依赖、把 agent 补查的版本写回。这些需要时由 agent 用 exec_command 自行在服务器上完成。
