# 软件清单用固定只读命令采集，sshmgr 不做漏洞比对

owner 要用外部的漏洞订阅程序判断哪些设备受某条漏洞公告影响，sshmgr 为此提供结构化的软件清单。这里定了两件事。

## Decision

**一、日常的实测采集由采集执行者跑固定的只读命令完成，不交给 AI agent。** 采集执行者默认是权威端，权威端没有网络路径的设备可以指定一个客户端实例。这样做的理由有四条：
- 每次采集的命令和解析规则都一样，前后两次结果可以逐条比出变化；
- 不消耗 token；
- 版本号原样读自包管理器和注册表，不会被编造；
- 命令集事先审查过，没有临场发挥的副作用。例如 Windows 上的 `Win32_Product` 查询会触发 MSI 安装包修复，固定命令集里可以事先排除它。

agent 只在 owner 专门要求时出场，用来认领未识别进程、起草声明，结果由 owner 确认后才生效。

**二、sshmgr 只提供软件清单和导出，不接收漏洞公告，也不做版本比对。** 漏洞库、名称对齐、受影响版本区间的判断，都交给外部程序。sshmgr 能保证的只有清单本身：版本精确、来源可追溯、给出标准标识(软件包统一地址)，导出格式是 CycloneDX。

## Considered Options

- 由 agent 定期 SSH 上去盘点。它擅长认出非标准安装的软件，但输出不稳定，变化无法比较，还会持续消耗 token，因此没有采用。不过它的长处被保留在「认领未识别进程」这一环。
- sshmgr 内置漏洞比对，在 Web UI 里直接显示受影响的设备。这样 sshmgr 就要跟进漏洞库和版本区间的语义，越出了它「配置中心」的职责，因此没有采用。

## Consequences

- 包管理器和注册表认不出的软件，只要监听了端口，就会以未识别进程的形式出现；不监听端口的手工安装软件采不到，只能靠声明补上。
- 暴露级别中的局域网、虚拟局域网、公网三档，实测无法判定，只能来自声明。
