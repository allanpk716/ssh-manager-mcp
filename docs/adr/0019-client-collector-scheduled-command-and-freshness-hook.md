# 客户端采集执行者由命令行定时运行，MCP 桥顺手补采

软件清单中有些设备的采集执行者是客户端实例。权威端不知道客户端何时开机，也不能替 owner 修改客户端机器的系统设置，因此需要决定这台客户端实例上的采集由谁定时触发。

## Decision

**一、客户端实例提供 `sshmgr inventory collect-assigned` 命令，日常定时执行由 owner 自建的操作系统计划任务完成。** 命令每次在线向权威端取本实例的采集分派，逐台经本机 SSH 能力执行固定只读命令集，并逐台把结果交给权威端；sshmgr 只在帮助文本里给出 launchd、cron 与 Windows 计划任务示例，不安装、不修改这些计划任务。

**二、客户端 MCP 桥的快照新鲜度轮询在每轮之后顺手补采。** 它复用同一条 `collect-assigned` 逻辑：发现本实例负责的设备超过一天没有成功结果，或有待执行的立即采集请求，就在后台执行；取分派或上交失败时直接结束本轮，不排队、不在客户端保存软件清单。计划任务与 MCP 桥用同一把实例本地锁文件互斥，锁被占用时直接跳过或失败，不并发执行。

## Considered Options

- 由权威端主动连接客户端并下发采集命令。这要求权威端能到达每台客户端，恰是「客户端实例作为采集执行者」要解决的限制，因此没有采用。
- sshmgr 替 owner 安装计划任务。这会把修改操作系统设置的权限交给应用，违背本功能不自动改系统设置的边界，因此没有采用。
- 客户端把结果先写到本地，等权威端可达后再上交。这会让客户端出现第二份软件清单事实源，也违背受审计转发写「不可达直接失败、不排队」的规则，因此没有采用。

## Consequences

- owner 要为每台作为采集执行者的客户端实例自建计划任务；不建也能靠 MCP 桥的新鲜度轮询补采，但客户端上长期没有 MCP 桥运行时，清单会过期。
- 客户端本地只保留 SSH 配置与凭据缓存，不保留软件清单和采集状态；权威端不可达时，采集分派、查询与导出都直接失败。
- 计划任务与 MCP 桥可能同时触发，但本地锁文件保证同一实例同一时刻只有一份采集在执行。
