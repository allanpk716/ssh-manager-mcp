# 桥热升级:首代桥自降级为泵,继任进程领养会话

桥的工具清单是编译期静态注册,而标准输入输出(stdio)形态的桥随宿主进程生灭、宿主对其掉线不自动重拉——`update` 的分支注释明文「运行中的桥继续旧版;新版本下次 agent 会话生效」,发版后正在开着的会话永远拿不到新工具,这是既成痛点。宿主侧事实:Claude Code 官方支持 MCP 的工具清单变更通知(tools/list_changed,交互式会话自动重拉清单、新工具跨轮次可用),`/mcp` 的 Reconnect 重跑注册命令可捡起新二进制——但重连要人动手且断连接。我们决定:**热升级做在桥进程自身,不依赖任何宿主私有能力——桥在空闲且盘上存在新代际二进制时,以领养模式拉起继任进程并把已握手的会话(协议版本等参数)交给它,自己退位;退位按代次区分:首代换手(桥的标准输入输出还直连宿主)父桥新建一对泵侧管道给继任(继任不接触宿主侧句柄)、自持宿主侧句柄化为泵(纯字节哑搬运)永居最外层;后续各代换手继任直接继承泵侧管道句柄、原桥退出,泵对端点换人无感知;继任就绪判定失败则不退位(=自动回退);换手完成后发一次工具清单变更通知,当前会话立即拿到新工具**。配套:`update` 落代际信号文件,桥轮询采纳(代际信号而非版本大小比较,降级回滚同样传播);新增 MCP 工具 reload_self(被动查询当前/盘上/GitHub 最新版本+强制触发);忙时(活跃隧道/后台任务/传输)拒绝并附活跃清单。不变式:**切换动作永不从网络取可执行代码**——取码只走 update 既有的校验链(HTTPS+跳转白名单+SHA256+staged 自检),轮询本地信号文件不给任何机器新增本地监听面。

## Considered Options

- **注册指向稳定壳进程(壳再拉当前二进制)**:被否——全机器全宿主重注册一遍(配对工件、.mcp.json 全要动)+ 永久双层进程,只买到「天生是壳」的洁癖;「服务器自降级为泵」这一过渡态写一次即可,此后各次升级行为两案相同。
- **复活 MCP-over-HTTP 远程面(宿主以 URL 直连 serve)**:被否——Plan 42 模式缩减时已刻意删除该面(「客户端一律本地只读缓存」是定过案的架构决策),复活要重做令牌模型、破坏离线缓存姿态;且远程面升级=重启 serve,不解决本机离线工具。
- **面向宿主的进程直接退场让新进程顶上**:被否——宿主只认它亲手拉起的那个进程,退场即显示掉线且 stdio 无自动重拉;故必须留一个永居最外层的泵,这是本机制的形状来源。
- **仅靠 /mcp 手动重连**:被否——不重启宿主但每会话每机手动一次,不解决「agent 正用着就要新工具」;保留为不支持清单变更通知的宿主的兜底路径。

## Consequences

- **最外层泵的代码冻结在「装机后第一个带机制的版本」**:泵只搬字节不碰协议,MCP 协议演进不需要它懂;这是有意接受的世代残留,代价集中在「降级过渡」一小段一次性代码。
- **会话领养是前后两个进程的内部契约**:继任者必须能以「已握手」状态起服务(会话参数随交接传递,就绪信号走文件),对宿主透明;意味着交接代码要随 MCP 协议演进持续维护。
- **换手瞬间要求零在飞请求**:忙判据=活跃隧道/在飞后台任务/进行中传输/在飞调用,拒绝时附活跃清单;后台任务终态保留期不算忙。
- **失败面如实列**:继任就绪判定失败→不退位,原桥继续服务并报错;继任者中途崩溃→泵退场→宿主显示掉线,手动重连(与今天桥崩溃同行为,不更糟)。
- **已知宿主小坑**:同一轮对话进行中注册的新工具可能报「无此工具」,下一轮恢复(Claude Code 已知问题);工具描述提示重试即可。
- **引导无法热上车(物理事实)**:机制自身发布后靠自然消亡换血——新拉起的桥即新版;仅当要升级正开着的会话时,手动 /mcp 重连一次。
- 直连形态(权威机)与缓存形态(工作机)走同一代码路径,多实例桥各自独立换血,互不影响。
