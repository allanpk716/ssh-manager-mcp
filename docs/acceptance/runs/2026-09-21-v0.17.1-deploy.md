## P2 本机部署+冒烟（含事故与恢复）

1. 下载 `sshmgr_0.17.1_windows_amd64.zip` + `checksums.txt`，sha256 **三方核对一致**：checksums.txt 行 = 本地 `sha256sum` = NUC10 更新时报告值，均为 `49f8082f…`。
2. 换装：`mv ~/bin/sshmgr.exe ~/bin/sshmgr.exe.bak`（0.17.0 留档）→ 新 exe 入位 → `sshmgr version` → `0.17.1`。在跑的 MCP 进程不受影响（Windows 允许改名运行中映像）。

### 事故：cache pull 令牌种类混用 → 设计内隔离销毁

3. `sshmgr cache pull` 首跑：url/pin 取自 `cache status` 与 NUC10 doctor 报告，但 `--token` **误从 `~/.claude.json` 的 ssh 启动参数里抠**——该位置的 `--token` 是 `mcp` 子命令的**项目令牌**（`projects add` 产），而 `cache pull --token` 要的是**设备授权码**（`cache-tokens add` 产）：同名旗标、两种令牌。项目令牌被 serve 按「未知/被拒设备码」401，客户端按 Plan 34 吊销语义执行**隔离**：快照隔离到 `quarantine/`，设备码与本地解密钥（DEK）删除——默认槽缓存（实例 laptop-v040）就此销毁。在跑的 MCP 进程凭内存态续命，会话通道未断。
4. 定位过程如实：先据 `cache-tokens ls` 前缀核对（所用令牌前缀与任何在册码不符）误判为「配置里躺着已吊销死码」；再经 `mcp --help` 澄清令牌种类两分（`--token projects add` vs `--token cache-tokens add`）方定位根因。v0.17.0 部署记录 §P2.3 的先例姿势本就是「url/token/pin 从本机 `cache.auth.json` 读入内存注入，不回显」——本轮未照抄该姿势是直接原因。教训与改进方向已登记 backlog 活跃面第 9 条。

### 恢复：新设备码再入网

5. NUC10 `sshmgr cache-tokens add --name laptop-v050 --profile e2e-profile` → 一次性授权码（不入册）。
6. 笔记本 `cache pull --url https://192.168.100.235:7878 --token <一次性码>:<服务器公钥指纹>` → `pulled 12 servers / 13 credentials`，**首入网自动落位具名实例槽** `instances\laptop-v050\`（Plan 40 批2 §1.2 首拉归位语义；与 v0.17.0 时代的默认槽布局不同）。服务端 `cache-tokens ls` 终态：laptop-v050 active、last_pull 当日 15:45。
7. `~/.claude.json` ssh 启动参数补 `--instance laptop-v050`（项目令牌原样保留；中途曾误把设备码换进令牌位，`mcp` 当场拒起「invalid or unknown token」，随即纠正——两令牌位不可互换的双向实证）。配置改动前备份 `.claude.json.bak-before-v050`。
8. 冒烟（MCP stdio 驱动脚本起新进程，`mcp --cache --instance laptop-v050`）：initialize 握手 serverInfo `ssh-manager 0.17.1`；tools/list **12 工具**全量；`list_servers` 离线解密返回 12 台服务器清单（与在线面逐台吻合；中文乱码为驱动脚本控制台编码的已知显示层现象）。
9. `sshmgr doctor` → **0 WARN, 0 FAIL**（client-cache[laptop-v050] PASS `cache.bin present`）。
