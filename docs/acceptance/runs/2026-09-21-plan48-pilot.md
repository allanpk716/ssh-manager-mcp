## A1 反馈场景三步复跑

- **步骤 1（笔记本经 MCP 工具对工控板 exec 一次）——延后**：本会话 ssh MCP 工具（笔记本 `sshmgr mcp --cache` 默认实例）对工控板 `echo ok` 的结果是网络层失败，未到 SSH 握手：

  ```
  ssh dial: dial tcp [REDACTED]: connectex: A connection attempt failed because the connected party
  did not properly respond after a period of time, or established connection failed because connected
  host has failed to respond.
  ```

  ping 192.168.1.108 两次 100% 丢包（开工时与收尾时各测一次，均不通）。板子断电/断线，物理操作属人工保留面。**不产生新的转发**（未到握手），也不影响既有锚。
- **步骤 2（NUC10 查转发行）——过**：`sshmgr audit --action pin-forward`（经 SSH 工具面在 NUC10 执行）：

  ```
  2026-09-10 16:02:26+08:00  生化高速工控板  (owner)  pin-forward  ok  exit=0  0ms
    host=192.168.1.108:22 fp=SHA256:SPr54CfOFODWyFymPCfmPFMSHDlFlPdprDxpWhv2GGA
    device=laptop-v040 via=forward affects=1 entries: 生化高速工控板
  ```

  判据②字段齐：设备名（device=laptop-v040）+ 指纹 + affects 清单。注意：这是 2026-09-10 首次锚定的**历史行**——本轮板子不可达，未产生新行。等值锚重复 exec 不写新审计行是设计行为（409 等值路径事务回滚、零仪式），板子上电后复跑若快照内锚在位，同样只会是静默匹配。
- **步骤 3（NUC10 显示已锚指纹）——过**：`sshmgr servers pin-hostkey 生化高速工控板`：

  ```
  host=192.168.1.108:22 fp=SHA256:SPr54CfOFODWyFymPCfmPFMSHDlFlPdprDxpWhv2GGA
  (format=blob, source=forward, device=laptop-v040, created=2026-09-10 16:02:26+08:00)
  ```

  判据③：显示指纹与转发行指纹逐字一致、`source=forward`、`device=laptop-v040`（笔记本设备名）。✓

**A1 判定**：②③过，①延后（owner 上电工控板后补跑一次 exec 即闭环）。

## A5 doctor 计数一致——过

全部经 SSH 工具面在 NUC10 执行：

1. `sshmgr doctor` → `vault-open: PASS copy-probe decrypted 12 servers / 14 credentials`（另：整体 0 WARN 0 FAIL）。
2. `sshmgr servers ls` → **12 台**（与 copy-probe 服务器数一致；无「差一」）。
3. `sshmgr ssh NUC10 -- echo a5-spot-check` → `a5-spot-check\r\n`，exit 0（口径抽查通）。
4. 凭据侧 14 vs 快照导出 13 的差：`sshmgr gc`（干跑）→ `1 orphan credential(s); rerun with --apply to delete`——doctor 数的是库全量、快照只导出 profile 引用集，差值恰为 1 条无主凭据，口径一致。

附（终审延后 rider「doctor busy 分支」）：本轮 serve 运行中直接跑 doctor 未触发 busy 降级行（vault-open 常规 PASS）。有意制造 busy 需要恰逢并发写事务，本轮未构造，维持登记。

## 工具与取证方式（agent 代跑的姿势记录）

- **本机 SSH 工具面**：会话的 ssh MCP server = 笔记本 `sshmgr mcp --cache --token <项目令牌>`（默认实例，`SSHMGR_CACHE_MAX_OFFLINE=24h`）。NUC10 侧一切命令经 `exec_command`（server_id `mymgHCZUMeE`）。
- **MCP stdio 驱动脚本**：为 A3/A6 写了一次性驱动（`mcp_driver.py`，存活于系统临时目录，不入库）——spawn `sshmgr mcp --cache [--instance X] --token <运行时从配置/临时文件读取，不回显不落盘>`，依次发 initialize / tools/list / tools/call，stdout/stderr 分流全量留档。这也是后续「起新进程」类验收步骤的复用姿势。
- **快照探针**：为排一笔录事故（见发现 1）写了临时 Go 探针（库内临时目录，已删除）：`LoadCacheSnapshotFor` 解密读默认实例快照，打印 servers/grants/projects/host_keys 的 id 类字段（零密钥），并复刻水合路径（临时库 + ImportSnapshot + VerifyToken + ServersForProfile）五轮。
- **取证纪律**：命令原文+完整输出如上；NUC10 执行处均已注明；一次性密钥材料（临时设备码、靶子条目口令、pair 项目令牌、会话项目令牌）明文一律不入册。
- **完整性对照**：本轮涉完整性断言的对照均为指纹/哈希逐字比对（A1 锚指纹 vs 审计行指纹；A6 靶子公钥指纹 vs 锚 vs 审计行三向一致），无落盘文件级 sha256 需求。

## 姿势层发现（试点的目的就是暴露这些）

1. **服务器 id 大小写敏感 + 抄录事故（agent 侧教训，非产品缺陷）**：NUC10 真实 id 是 `mymgHCZUMeE`（第二位小写 y），本 agent 一路抄成 `mYmgHCZUMeE`（大写 Y），导致 ~11 次 `exec_command` 全部 `ErrNotInProfile`（旁车审计均记 status=denied），一度被误判为「list 与 exec 口径不一致/不可复现抖动」；用字节级探针（Go `%q` 打印）才定位。错误文案「call list_servers to see the servers you may use」指引回列表，但肉眼看列表同样读错且复制链会固化同一错值。**回填 backlog：ErrNotInProfile 可加大小写近似提示（如 "did you mean mymgHCZUMeE?"）——本轮真实损失 ~40 分钟，值得。**
2. **`cache instances rm` 无无人值守通道（ADR 0003 缺口）**：护栏「stdin 不是 TTY 拒绝执行」防脚本误删，但也没有显式旗标/环境变量等价面——agent 代跑的清理步骤被拦（winpty 伪终端亦崩）。本轮遗留：临时实例 `plan48drill` 需 owner 在交互终端跑 `sshmgr cache instances rm plan48drill`（输入实例名确认）。已登记 backlog。
3. **owner 侧命令的审计盲区（A6 判据缺口的根因）**：`cache-tokens add/revoke`、`servers add/rm`、`profiles add/grant/remove` 均不写 vault 审计表（只有 exec / pin-* / pair.* / project.* / 转发等入册）。A6 的「revoke 有痕」按现状不可满足。已登记 backlog（判据不放宽）。
4. **册子步骤缺口已改册**：A6 原步骤 2 只写了 `pair --instance`，漏了 broker 侧审批动作（`serve pair ls` 核对 + `serve pair approve --profile`——profile 绑定正是在审批时发生）；已补步骤 2b。A6 步骤 6 的「pull 收敛」在步骤 4 吊销后不可达（401→按设计隔离销毁），已把两分支可达性写明。
5. **册子无状态表已补**：原册没有逐项状态表，判定结果只能外挂；已在册头加状态表（本记录的判定总表同构）。
6. **驱动脚本的编码坑（小）**：自写 stdio 驱动以 utf-8 读子进程输出时中文呈乱码（GBK 控制台链路），不影响判定；后续驱动脚本注意设子进程环境编码或对输出做替换处理。
