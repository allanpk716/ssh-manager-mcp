## C1 吊销 → 销毁 → 重新 enroll — 过

- 入网:`SSHMGR_PAIR_ASSUME_SAS=1 sshmgr pair --instance batch2drill --url … --pin …`(SAS 跳过已注明)+ NUC10 `serve pair approve --profile e2e-profile` → 首拉 12/13。
- NUC10 `cache-tokens revoke batch2drill` → 笔记本以靶子自己的凭据(`cache.auth.json` 运行时读入注入,不回显)再拉 → 服务端 401 → **销毁链完整**:
  - 三段式报文(快照隔离到 quarantine/ + 设备码与解密钥已删 + 再入网指引);
  - `manifest.json`:`{"state":"done","reason":"server rejected device code","steps":{"auth":"ok","bin":"ok","dek":"ok","meta":"ok"}}`——**四步销毁逐项 ok**(DEGRADED 分支未触发 = 全成功路径,如设计);
  - `cache status --instance` 报隔离态;槽内仅剩 config 与产物文件。
- 恢复:`pair --force` + 批准 → 新码落位,槽四件重建,12/13 健康态;服务端同名行翻回 active 并换新码。

## C2 到龄自废 → 重拉恢复 — 过(形态比册子预期更烈,如实登记)

- 上限入册:册子设想的「2m 短上限省时等价」**不成立**——上限校验硬地板 **≥1h**(`invalid SSHMGR_CACHE_MAX_OFFLINE "2m": must be a Go duration >= 1h`),按最小 1h 执行并如实登记;`--max-offline` 旗标持久化路径实证(`cache config` 显示 `cap: 1h0m0s (source: file)`);环境变量形式只作用于当次拉取、**不写文件**(env 拉取后 config 仍为旧值)。
- **第一发探针揭示交互**(如实留档):无环境变量起 `mcp --cache` 时默认 `--cache-max-age 30m` 会**先自动拉新再加载**,65 分钟旧缓存被自动续鲜、拒载不触发——到龄咬的是「真正离线超过上限」的机器,在线机器永续鲜(设计语义,认知订正)。正确探针须 `--cache-max-age 0` 禁自动拉。
- 拒载(到龄 1h+,`--cache-max-age 0`、无环境变量上限):**拒绝服务 ✓,且直接走隔离销毁**(同 C1 销毁链,报文首行 reason 为 `snapshot expired (offline beyond SSHMGR_CACHE_MAX_OFFLINE)`——到龄契约文案 ✓)。形态登记:比册子「拒载」预期更烈(拒载即销毁,非保留拒载);报文第二段的 `(token revoked?)` 提示对到龄场景**误导**(该场景码并未吊销)——已登记 backlog。
- 恢复:同码再拉已不可能(码随隔离删除)——走报文指引的再入网路径:`pair --force` 撞 419(见 plan-46-45 记录,顺带实证)→ 按 419 指引 broker 侧吊销 → 重试 `pair --force` + 批准 → 12/13 恢复 ✓(册子第 5 步「同码再拉恢复」的假设据此订正)。
